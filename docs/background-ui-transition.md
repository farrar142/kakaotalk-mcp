# 전환기 — 창을 앞으로 가져오지 않는 카카오톡 조작으로 (2026-11-12)

`background-ui` 브랜치에서 한 일을 처음부터 끝까지 적는다. 무엇을 바꿨는지는 `CHANGELOG.md`에,
항목별 진행은 `TODO.md`에 있다. 이 문서는 **왜 그렇게 했는지, 어디서 막혔고 무엇을 배웠는지**를 남긴다.

## 1. 출발점 — 무엇이 문제였나

다른 PC에서 kakaomcp 세션이 서버를 돌리며 8개 방을 5분마다 기록하고 있었다. 그 PC에서 두 가지가 보고됐다.

- **포커스를 빼앗는다.** 메시지를 읽을 때마다 채팅방 창이 맨 앞으로 왔다. 다른 일을 하던 사람의 입력이 끊겼다.
- **클립보드를 덮어쓴다.** Ctrl+A/C로 메시지를 읽고 나면 사용자가 복사해 둔 것이 사라졌다.

원인을 따라가 보니 뿌리는 하나였다. 버튼·메뉴·대화상자를 **화면 글자 인식(OCR)** 으로 찾고 있었고,
OCR은 화면 픽셀을 찍어야 하니 창을 앞으로 가져와야 했다. 클릭도 실제 마우스를 움직이는 방식이었다.
OCR은 느리고(창마다 수백 ms) 배율·테마에 흔들렸으며 '톡게시판'을 '특기시단'으로 읽는 일도 있었다.

## 2. 방향 — OCR 대신 무엇으로 알아볼까

카카오톡 PC의 버튼·메뉴·대화상자는 대부분 **모양과 위치가 고정**이다. 그래서 글자를 읽는 대신
다음 다섯 가지로 바꿔 나가기로 했다(`TODO.md`의 기호).

| 기호 | 방법 |
|---|---|
| **W** | Win32 판별 — 창 크기·클래스·소유자·컨트롤 ID |
| **K** | 키보드 — 대화상자에 `WM_CLOSE`(=취소), 메뉴는 ↓ N번 + Enter |
| **P** | 고정 위치 — 창 기준 좌표(배율 보정)에 게시된 클릭 |
| **I** | 이미지 매칭 — 기준 그림(템플릿)과 비교 |
| **T** | 글자가 매번 다른 곳만 OCR 유지(검색 결과 제목, 게시판 글) |

원칙: 한 번에 한 항목씩, 실물로 재고, 고친 것은 체크한다. 사용자가 정한 대로 빈틈 채우기는 하지 않고,
기록이 필요하면 기록 기능을 켜 둔다.

## 3. 기반 작업

### 창을 앞으로 가져오지 않고 찍기
`ImageGrab`(화면 찍기)을 `PrintWindow(PW_RENDERFULLCONTENT)`(창 자체 찍기)로 바꿨다.
비교해 보니 차이는 창 테두리 1px뿐이고 OCR 결과도 같았다. 자식 창 18ms, 메인 창 64ms.
아래 광고(Chromium) 영역은 안 찍히지만 필요 없는 부분이다. 최소화된 창은 여전히 못 찍는다.

### 포커스 없이 클릭 — 그리고 "가끔 무시된다"
가장 안쪽 자식 창에 `WM_MOUSEMOVE` → `WM_LBUTTONDOWN/UP`을 `PostMessage`로 보낸다.
여기서 첫 번째 함정을 만났다. **메뉴를 닫은 직후 다시 누르면 거의 무시된다**(0.6초 간격 0/8, 3초 간격 5/6).
그래서 클릭 뒤 결과(새 창, 화면 변화)를 확인하고 안 됐으면 1.5초 뒤 다시 누르는 방식이 기본이 됐다
(`BACKGROUND_CLICK_ATTEMPTS`). 반대로 "만들기 확인"처럼 두 번 눌리면 안 되는 곳은
양식이 닫혔거나 새 창이 떴으면 절대 다시 누르지 않는다.

### 백그라운드 읽기와 클립보드 복원
Ctrl+A/C를 메시지 목록에 직접 `PostMessage`하고, Ctrl은 카카오톡 입력 스레드의 키보드 상태로 눌러 둔다.
정해진 대기 대신 클립보드 시퀀스 번호가 바뀌는 순간 읽고, 읽은 뒤 원래 클립보드(글 외 형식 포함)를 되돌린다.
이것으로 보고된 두 문제가 모두 풀렸다.

### 배율 보정·템플릿
- `screen.dpi_scale` / `screen.px`로 고정 좌표에 배율을 씌웠다. 이 PC는 100%라 다른 배율은 단위 시험으로만 확인했다.
- 템플릿은 100% 기준 회색조 PNG(`src/kakao_mcp/templates/`). 어두운 픽셀끼리 맞춰 비교하고 ±3px 이동을 허용한다.
  부르는 쪽은 `templates.window_matches(hwnd, name)` 하나만 쓴다.

## 4. 막힌 곳과 배운 것

### 크기만으로는 창을 구분할 수 없다
링크 확인창(261x180 안팎)과 1:1 방 나가기 확인창(260x178)이 거의 같은 크기였다. 크기만 보고 닫았다면
엉뚱한 창을 건드릴 수 있었다. 첫 템플릿 `link_warning`('주의' 글자 그림)을 더해 구분했다.
같은 창이 두 PC에서 262x182와 260x178로 달라서 기준 크기는 둘 사이로 잡았다.

### Enter는 위험한 쪽 버튼일 수 있다
링크 확인창에서 Enter는 **연결하기**(브라우저가 열림)였다. 그래서 닫기·취소는 모두 `WM_CLOSE`로 하고,
Enter를 "확인"용으로 쓰지 않는다는 규칙을 세웠다. 나가기 확인창에는 Enter를 시험조차 하지 않았다.

### 메뉴에서 ↑ 한 번이 '채팅방 나가기'
새로 연 메뉴에서 ↑를 누르면 맨 아래 항목, 즉 방 메뉴에서는 '채팅방 나가기'로 간다.
실험 중 이것 때문에 나가기 확인창이 6개 떴고 모두 `WM_CLOSE`로 취소했다. 이후 ↑는 금지했다.

### 같은 크기의 메뉴, 다른 배치
오픈채팅 방 메뉴는 방장과 참여자 모두 179x335인데 배치가 달랐다. 방장의 맨 아래(52px)는 '채팅방 나가기',
참여자의 맨 아래는 **'신고하고 나가기'** 였다. 위치만 믿었다면 참여자 방에서 신고를 누를 뻔했다.
그래서 `ROOM_MENU_LAYOUTS`는 크기마다 후보 위치를 여러 개 두고, '채팅방 나가기'는 글자 템플릿
`menu_leave`가 **정확히 한 줄**에서만 맞을 때 고른다(참여자 메뉴에서 52px 1.0, 78px 0.0).
표에 없는 크기면 아무것도 누르지 않는다.

### 개인정보 — 닉네임이 조용히 무시됐다
「기본프로필만 참여 허용」 방에 닉네임으로 참여하면, 프로필 설정 창(300x251)에 프로필 선택이 없어서
닉네임이 무시되고 **실제 카카오톡 프로필로 참여**됐다. kakaomcp 세션이 찾아냈다.
이제 랜덤·닉네임 참여인데 프로필 선택이 있는 창(300x307)이 아니면 `WM_CLOSE`로 취소하고
`error_code: "kakao_profile_only"`를 돌려준다. 카카오톡 프로필로 다시 참여할지는 사용자가 정한다.

### 시험방으로 띄울 수 없는 창
커뮤니티 동의·세이프봇·이용자보호조치(짧은 시간에 여러 방 참여) 창은 일부러 띄울 수 없었다.
억지로 재지 않고, 실제로 뜨면 크기와 버튼 줄 그림을 `%LOCALAPPDATA%\kakaotalk-mcp\dialogs`에
종류·크기마다 한 번 남기도록 했다(이 PC 안에만). 모이면 **W**+**I**로 바꾼다.

## 5. 두 세션의 협업

이 PC의 세션과 다른 PC의 kakaomcp 세션이 같은 브랜치에서 나눠 일했다.

- 계정이 서로 달라서, 시험방은 이쪽이 **방장**으로 만들고 kakaomcp 세션이 **참여자**로 들어왔다.
  덕분에 방장·참여자 메뉴와 나가기 확인창(260x312 / 260x210)을 둘 다 실물로 쟀다.
- kakaomcp 세션이 가진 수정(이용자보호조치 감지, 빈 메뉴, `LinkGuard` 엄격 모드)은 이쪽에서 합쳤고(eeb1cfc),
  접근성 트리 조사 결과는 그쪽이 커밋했다(ae3f8bb, `docs/accessibility.md`).
- 그쪽이 기록 중인 8개 실제 공개방에서는 참여·나가기 시험을 하지 않았다.
- 시험방 세 개(mcp시험방7319·8426·5173)는 만들고, 시험하고, 방장 나가기로 지웠다. 검색 결과 0건으로 확인했다.

지킨 규칙: 오픈채팅방에는 메시지를 보내지 않는다. 메시지 전송은 허락받은 1:1 방에서만 하고 나머지는 읽기만 한다.
실험 중에도 채팅 내용은 출력하지 않고 개수·길이만 봤다.

## 7. 남은 것

- 커뮤니티 동의·세이프봇·이용자보호조치 창 — 저장된 그림이 모이면 OCR을 걷어낸다.
- 1:1·단톡방 나가기 확인창은 아직 OCR.
- 오픈채팅 방 소개 붙여넣기와 오픈채팅 창 열기는 아직 창을 앞으로 가져온다.
- 게시판 탭 클릭이 무시됐는지 확인하는 방법.
- 다른 배율(125%·150%)에서 실물 확인.
- 검색 결과·게시판 글 제목은 내용이 매번 달라 OCR(**T**)을 유지한다.
